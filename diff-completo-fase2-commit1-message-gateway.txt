ARQUIVOS NOVOS

1. `server/gateways/OutboundMessage.ts`
O que foi criado:
- interface `OutboundMessage`

Campos:
- `executionId`
- `recipient`
- `content`
- `metadata?`

Efeito prático:
- o envio deixa de depender apenas de parâmetros soltos do serviço atual
- existe agora um contrato explícito de mensagem de saída

2. `server/gateways/GatewayResult.ts`
O que foi criado:
- tipo `GatewayStatus`
- interface `GatewayResult`

Status definidos:
- `ACKED`
- `FAILED`
- `TIMEOUT`

Campos:
- `status`
- `attempt`
- `occurredAt`
- `providerMessageId?`
- `providerMetadata?`

Decisão importante:
- foi usado `occurredAt` em vez de `timestamp`
- isso evita ambiguidade com timestamps internos do domínio

Também foi adotado:
- `providerMessageId?`
- `providerMetadata?`

Motivo:
- o contrato já nasce preparado para integrações reais futuras sem quebrar compatibilidade depois

3. `server/gateways/MessageGateway.ts`
O que foi criado:
- interface `MessageGateway`

Contrato:
- `send(message: OutboundMessage): Promise<GatewayResult>`

Decisão arquitetural importante:
- nenhuma lógica de retry
- nenhuma lógica de budget
- nenhuma lógica de orquestração
- nenhuma decisão de negócio

Efeito prático:
- o gateway nasce como abstração pura, exatamente como pedido

4. `server/gateways/index.ts`
O que foi criado:
- barrel export dos contratos do gateway

Efeito prático:
- facilita a injeção posterior no `ExecutionService`
- centraliza o ponto de import da abstração
