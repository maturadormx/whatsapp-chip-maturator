CAPACIDADE ENTREGUE

M12 — Scheduler
- `SchedulerPort`
- `IntervalScheduler`
- `ProcessPendingObservationsUseCase`

Fluxo:
- `IntervalScheduler` dispara em intervalo fixo
- chama `ProcessPendingObservationsUseCase`
- o caso de uso lista `Observations` pendentes
- reenvia cada uma para o `ObservationPipeline`

M13 — Retry
- `RetryExecutionServiceDecorator`
- encapsula `ExecutionServicePort`
- 3 tentativas por padrão
- atraso exponencial simples:
  - `baseDelayMs * 2^(attempt-1)`

CORREÇÃO IMPORTANTE — FIM DO REPROCESSAMENTO INFINITO

Antes:
- `ObservationRepository` apenas salvava e recuperava por id
- o scheduler, se introduzido assim, poderia reprocessar para sempre a mesma entrada

Depois:
- `ObservationRepositoryPort` passa a expor:
  - `listPending()`
  - `markProcessed(id)`
- `MemoryObservationRepository` agora guarda:
  - `observation`
  - `processed`

Regra:
- quando o pipeline termina com sucesso:
  - `repository.markProcessed(observation.id)`

Consequência:
- apenas falhas reais permanecem pendentes
- o scheduler reprocessa somente o que realmente ficou incompleto

RUNTIME COMPARTILHADO

Arquivo:
- `server/runtime/observationRuntime.ts`

O que ele centraliza:
- `DevLogger`
- `MemoryObservationRepository`
- `MemoryEventStore`
- `DefaultRuleEngine`
- `DefaultExecutionService`
- `RetryExecutionServiceDecorator`
- `ObservationPipeline`
- `InboundService`
- `ProcessPendingObservationsUseCase`
- `IntervalScheduler`

Motivo:
- `Inbound` e `Scheduler` precisam operar sobre o mesmo repositório e o mesmo pipeline
- isso evita instâncias paralelas sem estado compartilhado

INTEGRAÇÃO NO BOOTSTRAP

Arquivo alterado:
- `server/_core/index.ts`

O que mudou:
- `createObservationRuntime()` é criado no bootstrap
- `registerInboundRoutes(app, { service: observationRuntime.inboundService })`
- `observationRuntime.scheduler.start()`

Com isso:
- HTTP usa o pipeline compartilhado
- scheduler roda no mesmo processo e reusa o mesmo estado

DETALHES DO RETRY

Arquivo:
- `server/infrastructure/decorators/RetryExecutionServiceDecorator.ts`

Comportamento:
- tenta executar o plano até `maxAttempts`
- em falha:
  - registra `execution.retry.failed`
  - espera o atraso configurado
  - tenta de novo
- em sucesso após retentativa:
  - registra `execution.retry.success`

NÃO FAZ AINDA:
- retry persistido
- dead-letter queue
- política configurável por tipo de ação
