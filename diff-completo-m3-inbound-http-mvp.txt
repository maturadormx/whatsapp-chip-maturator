TASK-000 — LEITURA REAL DA BASE

Antes de implementar, a estrutura do projeto foi verificada.

Conclusões importantes:
- runtime HTTP real: `Express`
- entrypoint do servidor: `server/_core/index.ts`
- registro de middleware/rotas já acontece no bootstrap do `Express`
- portanto, o encaixe correto do `Inbound` é:
  - `server/inbound/...`
  - registro em `server/_core/index.ts`

Decisão importante:
- não foi criada árvore nova em `src/`
- não foi assumido `Nest`, `Fastify` ou outro framework
- a implementação respeita o esqueleto real do repositório

TASK-001.1 — INBOUND HTTP MVP

Arquivos criados:
- `server/inbound/dto/InboundEventDto.ts`
- `server/inbound/InboundService.ts`
- `server/inbound/InboundRouter.ts`
- `server/inbound/index.ts`
- `server/inbound/InboundRouter.test.ts`

Arquivo alterado:
- `server/_core/index.ts`

O que foi entregue:

1. DTO validado com `zod`
- `source` obrigatório
- `eventType` opcional
- `payload` opcional
- `correlationId` opcional
- `timestamp` opcional

2. `InboundService` placeholder
- aceita um evento válido
- responde com:
  - `status: "accepted"`
  - `id`

Importante:
- nesta etapa não há regra de negócio
- não há roteamento para `Fact`
- não há `Policy`
- não há gravação em `Event Store`

3. `InboundRouter`
- registra:
  - `POST /api/inbound/events`
- retorna:
  - `400` para payload inválido
  - `202` para payload válido

4. Registro no runtime real
- `registerInboundRoutes(app)` foi acoplado ao bootstrap do `Express` em `server/_core/index.ts`

DECISÕES ARQUITETURAIS IMPORTANTES

1. Endpoint mínimo
- esta rodada cria só a camada HTTP de entrada
- nenhuma regra de domínio foi deslocada para o endpoint

2. Placeholder explícito
- `InboundService` existe para marcar a fronteira do módulo
- ainda não é orchestrator, policy nem adapter para Event Store

3. Compatibilidade com a baseline 2.0
- `Inbound` entra como camada periférica
- o núcleo protegido continua intacto:
  - `ExecutionService`
  - `RetryService`
  - `MessageGateway`
  - `Clock`
  - `BehaviorActionLedgerRepository`
